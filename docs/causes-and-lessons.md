# 前面讨论的问题：原因分析与经验总结

真机性能取决于整条链路：现场装配与输入、观测和动作语义、示范覆盖、训练利用方式、部署执行、测评判定。先定位哪一环出了问题，再决定恢复配置、补采数据还是调整方法。

下面把前面讨论的十个核心问题整理为结论、原因和处理依据。**这里没有新增现场测试；公开案例中的已报告事实、通用机制与待验证原因分别说明。** 对照案例见 [三篇公开实战复盘](case-studies.md)，逐项排查见 [30 项问题表](problem-index.md)。

双臂 Piper 的具体补充见 [擦黑板现场复盘](blackboard-wiping.md)：把掉臂／甩臂、接触失败、相机槽位、夹爪标签和 EEF-rel 接口分别定位。该篇区分受限材料核对、月报陈述和工程建议，没有新增真机测试。

<a id="an-01"></a>
## AN-01 数据最重要，训练脚本为什么还能改变真机性能？

**结论：优先保证数据及接口正确，再用固定评测比较训练与部署方法。相同数据可以被正确利用，也可以因处理或执行错误而失效。**

训练脚本会决定给模型看什么图像、预测什么动作、哪些样本更常出现，以及用什么尺度和目标优化。归一化、时间配对或动作参考系有误时，增加数据仍会沿用错误含义；采样和微调范围不合适，也可能让少量关键接触动作被大量简单动作淹没。

loss 通常统计某种离线预测误差。真机任务还要求多个阶段连续成功：接近大致正确、闭爪偏一点，就可能整条失败。策略到达训练中少见的状态后，后续误差还会继续累积。因此 loss 下降只支持“更好地优化了这个离线目标”，没有直接测量自主成功率。

| 观察到的模式 | 优先核查 | 处理方向 |
|---|---|---|
| 几乎所有摆放都沿同一方向偏 | 相机／标定、单位、坐标、动作重建 | 先修正配置与语义 |
| 熟悉位置成功，边缘或新朝向失败 | 独立示范的条件分布 | 定点补采并保留正常分布 |
| 动作段之间停顿，图像和指令变旧 | 推理、网络与执行时序 | 分析部署耗时与重规划 |
| 同批数据、同现场下配置表现不同 | 训练配方和检查点选择 | 固定协议做对照 |

这些模式是诊断线索，不能仅凭现象判定根因。**经验总结：先排除系统性语义错误，再用失败分布决定数据投入；方法收益通过同条件闭环测评确认。**

依据：[RUN-01～04](training-and-deployment.md)、[A01](../resources/articles-and-code.md#a01)、[A02](../resources/articles-and-code.md#a02)、[A03](../resources/articles-and-code.md#a03)。

<a id="an-02"></a>
## AN-02 相机挪一点为什么会影响？腕部相机本来就在动

**结论：要管理相机的安装关系及实际模型输入。腕部相机随手臂运动是正常观测变化，支架松动则改变了这套关系。**

外部相机移动后，同一物理场景的像素位置、尺度、遮挡都可能变化。腕部相机支架重装后，同一机械臂姿态也会生成不同画面。若示范只覆盖原有视角，策略没有充分依据适应新的输入分布。

另一个原因是预处理：相机没移动，裁剪、缩放或镜像改变，也会让模型实际看到不同内容；原始预览看得到杯柄，保存后可能已经被切掉。

处理时先对照同一机器人姿态、同一物体摆放的基准输入，核对相机身份、安装和预处理，再考虑跨视角数据。显式几何变换只会影响使用它的模块；更新手眼外参不会自动改变未使用外参的图像策略。

**经验总结：工位照片、安装标记、基准画面和输入配置要随数据保存。部署需要变化的视角，才有计划地纳入采集和评测。**

依据：[CAM-01～03](camera-and-calibration.md)、[案例 CS-01](case-studies.md#cs-01)。这些机制不能证明任意小幅移动都会使所有模型失败。

<a id="an-03"></a>
## AN-03 校准文件丢了，为什么旧数据和模型可能不能继续用？

**结论：真正影响兼容性的是程序最终使用的映射发生了什么变化。文件找不到、恢复原版本、重新标定是三种不同情况。**

以关节校准为例，软件需要把传感器读数解释成关节角。若新校准改了偏置或方向，相同的训练数值就可能对应不同物理姿态。图像仍然清楚，训练和部署的动作含义却已经不一致。

公开案例 A01 中，作者报告临时位置的关节校准文件丢失，随后不正确的重新校准改变了偏置。不能把这概括为“文件一丢，机械臂物理零位立刻改变”；路径、机器人 ID 或容器挂载错误也可能只是让程序找不到原文件。

| 文件类型 | 改变时主要影响 |
|---|---|
| 关节校准 | 传感器读数、关节角与实际姿态的对应 |
| 相机内参 | 像素与成像几何的对应 |
| 外参／手眼标定 | 相机与基座／手腕等坐标系的变换 |

先核对实际加载位置、硬件身份和版本，优先恢复原映射；确需重标定时按本型号流程操作，再验证旧数据兼容性。恢复旧映射、转换数据或重采的选择由变化内容决定。

**经验总结：标定属于数据含义的一部分。数据、模型、装配和标定版本应能互相追溯。**

依据：[CAM-04～05](camera-and-calibration.md#cam-04)、[案例 CS-01](case-studies.md#cs-01)。SO-101 的具体校准步骤不直接适用于 Piper。

<a id="an-04"></a>
## AN-04 USB 掉线、画面互换和录制卡顿，分别为什么发生？

**结论：先区分身份、传输和处理环节，修复方式才有针对性。**

| 现象 | 可能机制 | 支持判断所需证据 | 对应处理 |
|---|---|---|---|
| 重启后腕部与桌面画面对调 | 动态编号重排，设备身份绑定不稳定 | 设备枚举和逐台画面对应 | 唯一序列号或稳定物理路径 |
| 设备消失后重连 | 线缆／接头、供电、控制器或驱动链路异常 | 同时刻内核与相机日志 | 对照替换具体链路部件 |
| 多路高负载才出现断流或超时 | 共享带宽、传输模式或处理吞吐不足等 | USB 拓扑、实际速率和多路负载记录 | 按瓶颈调整连接与采集参数 |
| 系统设备在线，但一录制就跟随变慢 | 取图、编码或写盘阻塞控制 | 各环节耗时与队列积压 | 拆分循环并保持时序关联 |

稳定命名针对身份问题；有源 Hub 可能改善供电，但共享上行带宽仍然有限。修改数据集的 FPS 字段也不会补回丢失的图像或修正旧时间戳。

**经验总结：先保留错误发生的时间和分环节日志，再做单项对照；恢复后用正式多设备负载验证。**

依据：[IO-01～05](capture-and-storage.md)、[A01](../resources/articles-and-code.md#a01)、[案例 CS-02](case-studies.md#cs-02)。原文报告的同型号相机身份问题不足以独立确定物理掉线根因。

<a id="an-05"></a>
## AN-05 Linux 采集电脑、转换器和几条线，各自解决什么？

**结论：现场电脑需要能稳定访问机器人和传感器。Linux 是软件运行环境要求，虚拟机是可选部署方式。**

常见 Piper 链路为电脑通过 USB-to-CAN 连接机械臂控制总线，相机另行向电脑送图像，机械臂由自己的电源供电。转换器完成接口连接，不会自动整合相机数据、供电和遥操逻辑。

因此线缆数量由相机、适配器和套件布线决定：电脑可能经 Hub 接多个 USB 设备，但逻辑上仍有控制、图像、输入和供电这些链路。虚拟机透传与远程训练也不会自动解决现场设备访问和采样稳定性。

**经验总结：按“设备→接口→程序→保存字段”画连接图，逐条确认；硬件连上和数据链路接通分别验收。**

依据：[Piper 接线与流程](piper-start.md)、[C03 固定版本](../resources/articles-and-code.md#c03)。具体接口和兼容性仍以型号与厂商文档为准。

<a id="an-06"></a>
## AN-06 鼠标怎么控制真实机械臂？适配是在做逆动力学吗？

**结论：输入设备表达意图，适配层把意图变成机器人支持的目标；是否需要逆运动学由动作接口决定。**

普通鼠标通常只有二维连续输入，需要按键或模式选择轴和旋转。SpaceMouse 可以表达三维平移与旋转，游戏手柄依赖摇杆和按钮映射。操作者可以直接观察真实机器人或真实相机画面，仿真不是这条链路的必要前提。

若输入是末端增量，而环境接受绝对关节目标，中间需要明确末端目标更新、坐标系、逆运动学及约束处理。若使用兼容主臂进行关节跟随，重点则是关节布局、方向、零位和初始化对齐。逆动力学关注运动需求对应的力／力矩，不能代替这些接口定义。

固定 RLinf 快照中的 Piper 环境接受关节目标，遥操声明没有现成兼容设备；把某个鼠标设备名填入配置，不能自动补出完整映射。

**经验总结：为输入、环境和硬件三层写清单位、绝对／相对、参考系与失效行为，再联调。**

依据：[TEL-02～03](teleoperation-and-actions.md#tel-02)、[C03](../resources/articles-and-code.md#c03)、[D02](../resources/articles-and-code.md#d02)。

<a id="an-07"></a>
## AN-07 开始和成功键是不是键盘上的？为什么能遥操却没采到数据？

**结论：控制、录制边界和任务结果是分别实现的功能；按键只是事件触发方式。**

机器人会移动，只证明输入已到达控制接口。录制器还要获取各相机、实测状态和下发动作，按正确时间配对，处理开始／结束事件并完成写盘。任一段未接通，都可能只得到预览或不完整文件。

开始与成功事件可以来自键盘、手柄或界面，由实际代码和当前模式决定。Piper 社区手柄教程里的 START 是模式切换、A 是位置保存，把它们理解为所有采集程序的录制键会造成流程误判。

一条有效示范需要准备、开始、执行、结果判定、保存完成和复位。操作者按下成功键还要对应真实完成条件，保留必要的结尾观察；停止写盘和机械臂停止各有自己的行为。

**经验总结：先录短轨迹并退出后回读，检查事件、字段与真实动作一一对应，再扩大采集量。**

依据：[TEL-01、04、05](teleoperation-and-actions.md)、[DATA-04](data-quality-and-coverage.md#data-04)、[D02](../resources/articles-and-code.md#d02)。

<a id="an-08"></a>
## AN-08 怎样提高覆盖？为什么多采一些仍然可能没有帮助？

**结论：覆盖相对部署范围定义，有限预算还要兼顾有效示范密度、关键组合和动作质量。**

任务范围扩大而预算不变，每类位置、朝向和物体组合可能只剩少量示范。连续拍摄产生很多相邻帧，独立场景却没有增加。随机摆放也可能集中在操作者习惯的位置，单因素分别出现过仍可能遗漏关键组合。

另一个缺口来自执行中间状态：训练全是理想抓取，部署抓偏后就缺少正确恢复动作。增加更多理想起点示范未必能覆盖这一阶段。常规专家 SFT 应学习正确动作，失败记录和纠正轨迹需要明确用途与边界。

实际安排：先固定一个可重复的小范围，确认示范准确且链路可用；记录条件矩阵和独立有效条数，再依据开发测评的失败位置、朝向、遮挡与阶段补采。最终验收条件独立保留。

**经验总结：增加独立有效经验及其条件标签；用条件覆盖和失败分布指导预算，不用总帧数代替覆盖。**

依据：[DATA-01～05](data-quality-and-coverage.md)、[案例 CS-01](case-studies.md#cs-01)、[案例 CS-02](case-studies.md#cs-02)。作者数据量不是通用最低条数。

<a id="an-09"></a>
## AN-09 RLinf 已开源，为什么还需要适配？示范微调和在线 RL 差在哪里？

**结论：开源部件提供起点，完整任务需要把硬件、遥操、录制、数据转换、模型和结果判定接成一致流程。**

本仓库核对的固定快照具备通用录制和 Piper 接口，但该版 Piper 的遥操声明为空、示例为 `teleop: none`。驱动能读关节，不足以证明末端输入、任务复位和训练部署已经完成。

示范微调主要学习数据中的期望动作；在线 RL 还需要可执行交互、奖励与结束定义、现场介入、复位和持续运行安排。更换训练入口并不能补齐这些任务条件。

判断“改了多少”应按层列出复用、修改和缺失的功能，用固定提交做对比，再核对实际行为。代码行数不能代表真机链路完成度。项目名也需结合来源识别，例如公开 AMD 教程里的 Phoenix 指电脑平台，不能据同名确认其他项目身份。

**经验总结：用功能与证据清单评估适配工作；每阶段留下可检查产物，尽早完成一个小任务闭环。**

依据：[Piper 能力与缺口](piper-start.md)、[C03 源码快照](../resources/articles-and-code.md#c03)、[工作流程](workflow.md)、[A04](../resources/articles-and-code.md#a04)。这里只对固定版本作说明。

## AN-10 怎样知道模型真变好了？多个 benchmark 怎样才算完成？

**结论：固定成功定义与条件，保留所有尝试，才能比较模型；完整流程和性能达标需要分别记录。**

相机、物体、检查点、时间预算或人工介入规则变化，都会让成功率差异混入其他因素。展示视频挑选成功尝试或省略推理等待，也会改变观看者对可靠性和速度的判断。

预录动作回放验证的是一组命令在特定条件下能否执行；自主闭环还要求策略根据新的观测决策。多次测评应能重算成功次数与分母，单列重试、介入、硬件异常和证据不足，并按条件查看失败阶段。

多个 benchmark 的完成应以预定义任务／协议为单元，关联数据质检、训练配置、检查点、部署、逐次结果和结论。同一任务多个检查点不会自然变成多个 benchmark；表现未达标也可以形成完整且诚实的测评闭环。

**经验总结：结果可信度来自可追溯的完整尝试和一致协议。先明确完成标准，再统计进度和性能。**

依据：[EVAL-01～05](evaluation.md)、[案例 CS-03](case-studies.md#cs-03)、[逐次评测记录参考](../resources/videos.md#e01)。
